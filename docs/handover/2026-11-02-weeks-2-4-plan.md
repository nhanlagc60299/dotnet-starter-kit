### Task 2: Ba DB role + audit append-only

Tạo `deploy/dokploy/postgres-init/` gồm script **idempotent**, chạy được cả lần đầu (mount vào `/docker-entrypoint-initdb.d`) lẫn trên DB đã có (`deploy/dokploy/scripts/db-roles.sh` gọi `psql` bằng superuser).

Yêu cầu:
- Extensions tạo bằng superuser: `pgcrypto`, `uuid-ossp`, `pg_trgm`, `unaccent`.
- `app_migrate`: LOGIN, owner của database (hoặc có CREATE trên DB), tạo/sở hữu mọi schema module. Không SUPERUSER.
- `app_runtime`: LOGIN; USAGE trên các schema; SELECT/INSERT/UPDATE/DELETE trên bảng, USAGE/SELECT trên sequence, qua `ALTER DEFAULT PRIVILEGES FOR ROLE app_migrate` (để bảng do migrator tạo sau này tự có quyền) **và** GRANT trên bảng đã có. Schema `hangfire` tạo sẵn và **owner là `app_runtime`**, vì Hangfire tự migrate schema lúc API start (`PrepareSchemaIfNecessary` mặc định true). Không có quyền CREATE trên các schema khác, không DROP/ALTER.
- `app_readonly`: LOGIN; SELECT trên mọi bảng (kể cả hangfire), qua default privileges + GRANT hiện có.
- Audit append-only: tìm schema/bảng audit (module Auditing) và REVOKE UPDATE, DELETE, TRUNCATE trên đó khỏi `app_runtime` (cả default privileges cho schema đó). Trước khi revoke, grep code Auditing xem runtime có UPDATE/DELETE audit row không (retention job…). Nếu có, ghi vào report và README (vi phạm nguyên tắc 2), không sửa code module.
- Vì default privileges chỉ áp dụng cho bảng tạo sau, script phải re-grant được: chạy lại sau mỗi lần migrate là an toàn (ghi rõ trong README: Dokploy chạy `db-roles.sh` thế nào/khi nào). Nếu migrator chạy bằng `app_migrate` thì default privileges đã đủ.
- Password lấy từ env (`APP_MIGRATE_PASSWORD`, `APP_RUNTIME_PASSWORD`, `APP_READONLY_PASSWORD`), không hard-code. Cập nhật `.env.example` và compose của Task 1 (mount init dir, connection string dùng role).
- Kiểm chứng local (ghi lệnh + output vào report): fresh volume → init tạo role → migrator (`app_migrate`) apply --seed exit 0 → api (`app_runtime`) `/health/ready` 200 và login `POST /api/v1/identity/token/issue` (header `tenant: root`, `admin@root.com`, password seed) thành công → `app_runtime` không `DROP TABLE` và không `UPDATE` bảng audit được → `app_readonly` không `INSERT` được. Chạy `db-roles.sh` lần hai không lỗi.

### Task 3: Backup Postgres → R2 + verify restore

Tạo service `backup` trong compose prod (luôn bật, vì backup là bắt buộc theo nguyên tắc 3). Image build từ `deploy/dokploy/backup/Dockerfile` (base `postgres:18-alpine` + `rclone` + `busybox crond`).

Yêu cầu:
- `backup.sh`: `pg_dump -Fc` bằng `app_readonly` → file `fsh-<UTC timestamp>.dump` → `rclone copy` lên remote S3-compatible (R2) cấu hình hoàn toàn qua env (`BACKUP_S3_ENDPOINT`, `BACKUP_S3_BUCKET`, `BACKUP_S3_ACCESS_KEY`, `BACKUP_S3_SECRET_KEY`, `BACKUP_S3_PREFIX`). Kèm file `.sha256`. Script **không xóa** gì trên remote. Retention do lifecycle rule của bucket R2 (ghi hướng dẫn trong README). Xóa file tạm local sau khi upload thành công.
- `restore-verify.sh`: tải bản dump mới nhất, kiểm sha256, `initdb` một cluster tạm trong container (không đụng DB prod), `pg_restore`, chạy sanity queries (đếm bảng theo schema, đếm user trong bảng user của Identity, kiểm có tenant `root`), in kết quả, exit ≠ 0 nếu thất bại, dọn cluster tạm.
- Lịch qua crond: backup hằng ngày (`BACKUP_CRON`, mặc định `0 2 * * *`), restore-verify hằng tháng (`RESTORE_VERIFY_CRON`, mặc định `0 4 1 * *`). Log ra stdout.
- `app_readonly` phải dump được (kiểm chứng; nếu thiếu quyền trên sequence/schema thì sửa script role của Task 2).
- README: mục backup/restore (cách chạy tay `docker compose exec backup backup.sh`, cách restore thật vào prod khi sự cố, cấu hình lifecycle R2, gợi ý Uptime Kuma push monitor nếu muốn).
- Kiểm chứng local: dùng RustFS (profile `storage` hoặc container tạm) làm S3 → chạy `backup.sh` thấy object trên bucket → chạy `restore-verify.sh` pass → làm hỏng sha256 thì verify fail.

Áp nguyên tắc apple-design ở mức vừa phải: phản hồi tức thì, chuyển động spring ngắn và ngắt được, tôn trọng `prefers-reduced-motion`, typography/khoảng trắng tiết chế. **Không thêm dependency animation mới** nếu app chưa có. Nếu cần thì hỏi (NEEDS_CONTEXT).
- Gate theo công tắc module (`useModules()` có sẵn ở dashboard; admin thì làm tương đương nếu cần) **và** theo permission; menu chỉ hiện khi module bật và user có quyền.
- Truyền dữ liệu per-call qua `mutate(arg)` (golden rule 9).
- Playwright route-mocked cho mỗi trang (happy path + một lỗi). `tsc -b` + eslint sạch.
- Kiểm chứng bằng mắt: chạy dev server với API mock (hoặc API thật nếu dựng được) và chụp màn hình mỗi trang (light + dark) vào report.
